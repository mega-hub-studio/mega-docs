◈ Run it for the team

◈ Chạy cho cả team

The UI is compiled into the binary, so publishing the app and publishing the web interface are the same job: expose one HTTP port, safely. Everything below differs only in who decides who reaches that port.

UI được biên dịch vào trong binary, nên publish app và publish web interface là cùng một việc: mở một cổng HTTP duy nhất, một cách an toàn. Mọi phương án dưới đây chỉ khác nhau ở chỗ ai quyết định ai tới được cổng đó.

First install

Cài đặt lần đầu

Three commands on the machine that will hold the index. Everything after this — who can reach it, how it stays up — is the rest of this page.

Ba lệnh trên máy sẽ giữ index. Mọi thứ sau đó — ai truy cập được, làm sao nó luôn chạy — là phần còn lại của trang này.

1
Configure the AI provider Cấu hình AI provider
cp .env.example .env# fill in AI_API_KEY, AI_BASE_URL, modelsmake live✓ checks both endpoints + embedding width

make live answers the question that actually bites: does this provider have /embeddings? Without it, indexing cannot run.

make live trả lời đúng câu hỏi hay gây đau: provider này có /embeddings không? Thiếu nó là không index được.

2
Index your documents Index tài liệu
make ingest DOCS=./docsindexed docs/retrieval.md (12 chunks) done: 8/8 files, 74 chunks

Only .md / .txt. For PDF or DOCX, convert first — markitdown spec.pdf > docs/spec.md. Re-running on the same path updates it in place.

Chỉ nhận .md / .txt. PDF hay DOCX thì chuyển trước — markitdown spec.pdf > docs/spec.md. Chạy lại trên cùng đường dẫn thì cập nhật tại chỗ.

3
Start it Chạy
make build && ./bin/knowledgemega-docs on http://127.0.0.1:8080

The UI is compiled into the binary, so there is nothing else to deploy. Verify the whole chain any time with make smoke: it indexes a fixture, asks a question only that file can answer, and checks the reply cites it.

UI được biên dịch vào trong binary, nên không có gì khác phải deploy. Kiểm tra toàn bộ chuỗi bất cứ lúc nào bằng make smoke: nó index một file mẫu, hỏi câu chỉ file đó trả lời được, rồi kiểm tra câu trả lời có dẫn nguồn đúng file.

Let the team in

Cho team truy cập

Three ways to give people the address, and the one setting that decides who reaches the port.

Ba cách đưa địa chỉ cho người dùng, và một setting quyết định ai chạm được vào port.

Read this first. This app has no accounts and no per-user permissions. Whoever reaches the port can read every indexed document and spend your provider key. It binds 127.0.0.1 by default for exactly that reason — the three options below differ only in who decides who reaches the port. Đọc phần này trước. App không có tài khoản và không có phân quyền theo người dùng. Ai tới được port là đọc được toàn bộ tài liệu đã index và tiêu API key của bạn. Chính vì vậy mặc định nó chỉ bind 127.0.0.1 — ba phương án dưới đây khác nhau đúng ở chỗ ai quyết định ai tới được port.

RECOMMENDED

No open ports, automatic HTTPS, and the team signs in with the company account. Identical whether the box is an office PC or a cloud VM — no port forwarding, no static IP, no firewall ticket.

Không mở port nào, HTTPS tự động, team đăng nhập bằng tài khoản công ty. Giống nhau y hệt dù máy là PC ở công ty hay VM trên cloud — không port forward, không IP tĩnh, không phải xin mở firewall.

sudo tailscale upBIND_ADDR=127.0.0.1 ./bin/knowledgesudo tailscale serve --bg 8080https://<machine>.<tailnet>.ts.net

Team installs the Tailscale app once, then opens that URL from anywhere — mobile data, hotel wifi, home.

Team cài app Tailscale một lần, rồi mở URL đó từ bất cứ đâu — 4G, wifi khách sạn, ở nhà.

Not Funnel. tailscale funnel publishes to the open internet and bypasses tailnet identity. If you use it, set AUTH_PASS. Đừng dùng Funnel. tailscale funnel đưa ra internet công khai và bỏ qua toàn bộ định danh tailnet. Nếu dùng, phải set AUTH_PASS.

For when the team must not install anything: a normal HTTPS address plus Google/Microsoft sign-in. Still no inbound ports — cloudflared dials out.

Dùng khi team không được cài thêm gì: một địa chỉ HTTPS bình thường cộng đăng nhập Google/Microsoft. Vẫn không mở port nào — cloudflared tự gọi ra ngoài.

cloudflared tunnel create knowledgecloudflared tunnel route dns knowledge kb.company.comBIND_ADDR=127.0.0.1 ./bin/knowledgecloudflared tunnel run --url http://localhost:8080 knowledge

Then add a Zero Trust → Access application for that hostname with the policy emails ending in @company.com. Nothing unauthenticated ever reaches the binary.

Sau đó thêm một application Zero Trust → Access cho hostname đó với policy email kết thúc bằng @company.com. Không request nào chưa xác thực tới được binary.

Simplest, and enough if nobody needs access from outside the office.

Đơn giản nhất, và là đủ nếu không ai cần truy cập từ ngoài công ty.

BIND_ADDR=0.0.0.0 AUTH_PASS='<long random string>' ./bin/knowledgeteam opens http://<office-pc-ip>:8080
Set AUTH_PASS anyway. Office wifi usually carries guests and personal phones. And because this is plain HTTP, the password travels readable — fine on a trusted LAN, not fine over the internet. Vẫn nên set AUTH_PASS. Wifi công ty thường có cả khách và điện thoại cá nhân. Và vì đây là HTTP thuần, mật khẩu đi trên đường truyền ở dạng đọc được — ổn trong LAN tin cậy, không ổn qua internet.

Upgrading

Nâng cấp

Four lines. The build step is not optional: the whole UI is compiled into the binary, so pulling without building leaves the old bytes being served.

Bốn dòng. Bước build không phải tuỳ chọn: toàn bộ UI được compile vào binary, nên pull mà không build thì vẫn đang phục vụ bytes cũ.

cd /opt/knowledge && git pull origin mainmake buildsudo systemctl restart knowledgecurl -s localhost:8080/api/health{"ok":true,"writes":true}

That last line is the check that matters: "writes":true means BA_PASS was picked up, so BA mode can publish. "writes":false means the instance is read-only.

Dòng cuối là chỗ cần xem: "writes":true nghĩa là BA_PASS đã được nhận, chế độ BA publish được. "writes":false là instance đang chỉ-đọc.

The front end needs nothing extra here: it is built by make ui into web/dist, which is committed, so make build on this host has no Node step and no network step. New settings arrive in .env; the table below says which ones exist and what each one costs to get wrong.

Frontend không cần thêm gì ở đây: nó được build bởi make ui ra web/dist, và thư mục đó được commit — nên make build trên host không cần Node, không cần mạng. Setting mới thì thêm vào .env; bảng bên dưới liệt kê có những gì và đặt sai thì mất gì.

One upgrade needs a re-index: check your stored paths first. Document paths are now stored relative to CORPUS_DIR. An index built before that change stored them differently, and a re-ingest would add a second document for every file — each one cited twice. Check, and rebuild if the answer says so: Có một lần nâng cấp cần index lại: kiểm tra path đang lưu trước. Path tài liệu giờ được lưu tương đối theo CORPUS_DIR. Index dựng trước thay đổi đó lưu kiểu khác, và một lần ingest lại sẽ thêm document thứ hai cho mỗi file — mỗi file bị cite hai lần. Kiểm tra, và dựng lại nếu cần:
sqlite3 knowledge.db 'select path from documents limit 3'spec.mdqa/ticket-1.mddocs/spec.md

A path like spec.md or qa/ticket-1.md is already relative to CORPUS_DIR — nothing to do. One that still carries the folder (docs/spec.md) or the full machine path predates the change, so rebuild:

Path kiểu spec.md hay qa/ticket-1.md là đã tương đối theo CORPUS_DIR — không phải làm gì. Path còn kèm tên thư mục (docs/spec.md) hoặc còn nguyên đường dẫn máy là loại cũ, nên dựng lại:

rm -f knowledge.db knowledge.db-wal knowledge.db-shm./bin/ingest docs

Deleting the index is safe, and cheap for a corpus this size: it is derived — CORPUS_DIR is the source of truth, confirmed answers included. The only cost is re-embedding, and the answer cache rebuilds itself on demand.

Xoá index là an toàn, và với corpus cỡ này thì rẻ: nó là thứ dựng lại được — CORPUS_DIR mới là nguồn sự thật, gồm cả câu trả lời đã confirm. Chi phí duy nhất là embed lại, còn cache câu trả lời tự dựng lại khi có người hỏi.

Three kinds of change need that same rebuild. There is no schema migration and deliberately so — the database is derived, so the upgrade path is to rebuild it. (1) A change to how documents are split into sections: the existing rows were split by the old rule and stay that way until re-ingested. (2) A new database column: schema.sql is CREATE TABLE IF NOT EXISTS, so an existing table never gains one, and queries naming it fail at runtime while passing on a fresh file. (3) A change to how a document path is stored. Everything else — a prompt edit, a new model, a retrieval parameter — invalidates the answer cache on its own and needs nothing. Ba loại thay đổi cần dựng lại như trên. Không có migration schema, và đó là chủ ý — database là thứ dựng lại được, nên cách nâng cấp là dựng lại. (1) Thay đổi cách chia tài liệu thành đoạn: các dòng đang có vẫn theo luật cũ tới khi ingest lại. (2) Thêm column mới: schema.sql chỉ có CREATE TABLE IF NOT EXISTS, nên bảng đã tồn tại sẽ không bao giờ có column đó, và query gọi tên nó sẽ lỗi lúc chạy dù test trên file mới vẫn xanh. (3) Thay đổi cách lưu path tài liệu. Còn lại — sửa prompt, đổi model, đổi tham số truy xuất — tự làm mất hiệu lực cache và không cần gì thêm.

Run it as a service

Chạy như một service

systemd, with the process confined to its own directory. Drop this in /etc/systemd/system/knowledge.service.

systemd, với process bị giới hạn trong thư mục của nó. Đặt file này vào /etc/systemd/system/knowledge.service.

[Unit] Description=mega-docs After=network-online.target Wants=network-online.target [Service] User=knowledge WorkingDirectory=/opt/knowledge EnvironmentFile=/opt/knowledge/.env ExecStart=/opt/knowledge/bin/knowledge Restart=always RestartSec=3 # its own directory and nothing else — that includes docs/, which a BA # confirm writes into, so keep the corpus inside WorkingDirectory NoNewPrivileges=true PrivateTmp=true ProtectSystem=strict ProtectHome=true ReadWritePaths=/opt/knowledge [Install] WantedBy=multi-user.target
sudo chmod 600 /opt/knowledge/.env# it holds the provider keysudo systemctl enable --now knowledgejournalctl -u knowledge -f

Re-index by hand, with the same one-liner, whenever the documents change. It exits non-zero if anything failed, so a failure is visible:

Index lại bằng tay, cũng đúng một dòng đó, mỗi khi tài liệu thay đổi. Nó exit khác 0 khi có lỗi, nên lỗi không bị chìm:

cd /opt/knowledge && ./bin/ingest docs
Don't add a timer yet. A schedule is worth it once the documents have a real change cadence — until then it re-indexes an unchanged corpus and spends embedding calls to do it. When that day comes it is this same line in a systemd timer or a cron entry, and nothing else changes. Chưa cần timer. Chỉ nên đặt lịch khi tài liệu thật sự có nhịp thay đổi rõ ràng — trước đó nó chỉ index lại một corpus không đổi và tốn tiền embeddings để làm việc đó. Đến lúc cần, vẫn là đúng dòng lệnh này trong timer systemd hoặc một dòng cron, không đổi gì thêm.
