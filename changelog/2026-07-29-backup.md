# 2026-07-29 — The database has a backup, and it is one script

`2026-07-28-no-backup.md` dropped the backup requirement — not deferred, removed. **That is
reversed here.** The reversal is written down rather than edited in, for the same reason that
entry gave for itself: it was true on its date, and this file is how the world moving on gets
recorded.

## Why it reversed, and it is not "we changed our minds"

The repo had already reversed it in the one place that cannot be argued with. `retiredClaims`
in [`web/embed_test.go`](../web/embed_test.go) — the enforcer rule 26 was written to add —
carries these two entries, added when the inversion landed:

```go
{"does not need a backup", "DB_PATH is the one file that does; losing it loses everything"},
{"dựng lại được nên không cần backup", "DB_PATH is the one file that does"},
```

So `make check` was asserting that *DB_PATH is the one file that needs a backup* while
`no-backup.md` said none was needed and `deploy.html` taught operators the same. That is a
second copy of a decision, disagreeing with the first, inside the gate — rule 17's failure
mode with a test behind the wrong half. One of the two had to die; the machine-checked one is
the one that was right.

What actually changed between the two decisions is the reason `no-backup.md` gave. It rested
on *one controlled entry point*, and on the database being derived: "deleting `knowledge.db`
costs an index, not a document — `ingest` rebuilds it". Both halves were true when written.
The second stopped being true the next day (`2026-07-29-db-is-the-source-of-truth.md`), and
one entry point protects a document from arriving twice, never from the file all of them live
in going away. `Remove` being soft protects a document somebody deleted; nothing protected
`DB_PATH`.

## What shipped

| | |
|---|---|
| [`scripts/backup.sh`](../scripts/backup.sh) | `sqlite3 .backup` of `DB_PATH` → `PRAGMA integrity_check` → publish to `DEST/knowledge-YYYY-MM-DD.db` → keep the newest `KEEP` |
| `make backup` | the same script, so the hand-run path and the timer cannot drift. `make backup DEST=… KEEP=…` |
| `deploy.html#backup` | the section: what it does, the two systemd units, and the restore drill |

Three choices worth not re-deriving:

- **`sqlite3 .backup`, not `cp`.** With WAL on, the file on disk is missing what is still in
  `knowledge.db-wal` — 2.4 MB of it on this host — so a `cp` under load yields a database
  that opens cleanly and is quietly short of the last writes. The online backup API takes a
  consistent snapshot with the server still answering, which is why nothing stops the unit.
- **Verify, then publish.** The snapshot lands next to the database and is only copied to
  `DEST` after `integrity_check` returns `ok`. A truncated file under today's name is worse
  than no file, because it reads like a backup.
- **`DEST` defaults outside the machine's disk** — `/mnt/c/Users/Public/knowledge-backups`.
  On WSL2 the Linux filesystem *is* a `.vhdx` inside Windows, so a copy beside the database
  shares its single point of failure. `Users/Public` because it exists on every Windows
  install and needs no administrator; `C:\` itself refuses the `mkdir`. On a Mac there is no
  `/mnt/c` and the script says so instead of inventing a directory.

`Persistent=true` is on the timer, and it is not decoration: WSL only runs while Windows
keeps it running, so `OnCalendar=daily` on a machine that was off at midnight misses
silently, for as long as the pattern keeps being missed. Without that line this is a backup
that works on a server and does nothing on the laptop it was written for.

## What was deliberately not built

Rule 20, applied — each of these is a decision with a trigger, not a backlog item:

- **No config knob and no route.** `internal/config` reads nothing new, so
  `TestEveryRouteAndKnobIsSpecified` has nothing to demand a section for. `DEST` and `KEEP`
  are shell variables a timer unit sets; the server has no opinion about them.
- **No compression.** The copy is a plain database, so restoring is `cp` back and a restart,
  and inspecting one is `sqlite3 <file> "select count(*) from documents"`. 6.9 MB does not buy
  a decompression step in front of a recovery.
- **No off-box copy.** `/mnt/c` survives the vhdx, which is this host's real single point of
  failure; it does not survive the machine. **Trigger: a second machine that is already
  trusted** — the tailnet has one — at which point this is a `DEST` on a mount, not new code.
- **No `make check` step.** The gate runs on a laptop and in CI, neither of which has a
  database worth backing up. A verified restore is an operator drill, and the Deploy page is
  where drills live.

## Measured, against the live deployment

`/opt/knowledge/state/knowledge.db`, service `active`, WAL 2.4 MB at the time:

- snapshot taken without stopping anything; `integrity_check` → `ok`
- the copy holds **9 documents · 313 chunks · 1 confirmed answer · `schema_version` 2** —
  the same counts as the source, so the WAL content is in it
- the temp snapshot next to the database was removed by the script's `trap`
- retention: 8 dated files plus today's → pruned to 7, newest kept
- `make backup` in a dev checkout wrote to `/mnt/c/Users/Public/knowledge-backups` and
  reported the path and size

Not yet done, and it needs `sudo`: **the two units are not installed.** Until
`systemctl enable --now knowledge-backup.timer` runs on this host, the only backup is the one
somebody types.

## Also: the `v0.13.0` tag was missing

`web/release.json` claimed `v0.13.0` while `git tag` listed nothing and
`git ls-remote --tags origin` returned nothing — so the badge asserted a version with no tag
behind it, which is exactly what rule 25 exists to prevent (`ReleaseInfo().Version` is meant
to be *empty* when no release was cut). `scripts/release.sh` does tag, so the tag was lost
after the fact, most likely to a rebase in a parallel session.

Repaired by tagging the commit that already held the file: `git tag -a v0.13.0 9fc9017`.
`git describe` now reads `v0.13.0-3-ge639e6d` — honest, and three commits past its own
release. **Not pushed.** The gap this leaves: `TestReleaseNotesAreGenerated` checks the
marker, the tag *shape* and a sha behind every line, but not that the tag exists in git — and
it cannot cheaply, because `actions/checkout` fetches no tags. So this failure mode is caught
by reading `git describe`, not by the gate.
