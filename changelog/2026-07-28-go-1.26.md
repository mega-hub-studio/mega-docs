# 2026-07-28 — Go 1.22.5 → 1.26, and the one thing that must happen on the host first

The floor in `go.mod` was `go 1.22.5`. Go 1.22 left support in August 2025, and the number
was doing active harm rather than just being old: `run.go` in golangci-lint derives its
target language version from `go.mod`, so **1.22.5 was silently muting the modernisation
linters** — they will not suggest an idiom the declared floor cannot compile.

Now `go 1.26`, which is the current stable line (1.26.5 at the time of writing; 1.25.12 is
the other supported one).

## ⚠️ Read this before the next deploy

**The deploy host needs Go 1.26 installed by hand, before `make build` runs there again.**
This is not a "should"; the build fails without it, and it fails in a way the usual escape
hatch does not cover.

`GOTOOLCHAIN` defaults to `auto`, which normally makes a go.mod floor self-healing — Go
downloads the toolchain it needs. That mechanism goes through the **module proxy**, and
this host cannot reach `proxy.golang.org` (recorded in
[`2026-07-27-wsl-deploy-and-import.md`](2026-07-27-wsl-deploy-and-import.md), worked around
with `GOPROXY=direct`). `direct` does not help here: there is no VCS to fetch a toolchain
from. Reproduced both ways:

```
$ GOTOOLCHAIN=go1.24.0 GOPROXY=off    go build ./cmd/server
go: download go1.24.0 for linux/amd64: toolchain not available

$ GOTOOLCHAIN=go1.24.0 GOPROXY=direct go build ./cmd/server
go: go.mod requires go >= 1.26 (running go 1.24.0; GOTOOLCHAIN=go1.24.0)
```

So the host's *installed* Go has to satisfy the floor on its own. And **not from apt** —
the host is Ubuntu 24.04, whose `golang` packages are 1.22, which is almost certainly where
`go 1.22.5` came from in the first place. From the tarball:

```bash
curl -fsSLO https://go.dev/dl/go1.26.5.linux-amd64.tar.gz
sudo rm -rf /usr/local/go && sudo tar -C /usr/local -xzf go1.26.5.linux-amd64.tar.gz
/usr/local/go/bin/go version          # go version go1.26.5 linux/amd64
```

`go.dev` and `github.com` are both reachable from that network — it is specifically
`proxy.golang.org` that is not — so the download itself is fine.

Verify in the deploy directory *before* pulling the change, because the failure is much
easier to read that way than as a broken deploy:

```bash
cd /opt/knowledge && go version && git pull && make build
```

## Why 1.26 rather than 1.25

1.25 would leave a release of headroom for a contributor on the older line. There is one
maintainer and one deploy host, so that headroom buys nothing real, and the ask was the
newest stable. Written as **`go 1.26`**, minor only — a patch-level floor (`go 1.26.5`)
would force every machine to a specific patch for no reason the code has.

## What the bump surfaced

Three findings, all `modernize/stringsseq`, all genuine — the Go 1.24 iterator forms, which
avoid allocating a slice just to walk it once. `make lint-fix` applied all three:

| file | was | now |
|---|---|---|
| `internal/aitest/provider.go` | `for _, word := range strings.Fields(…)` | `for word := range strings.FieldsSeq(…)` |
| `internal/rag/upload.go` (`SafePath`) | `for _, s := range strings.Split(clean, "/")` | `for s := range strings.SplitSeq(clean, "/")` |
| `web/spec.go` (`list`) | `for _, part := range strings.Split(v, ",")` | `for part := range strings.SplitSeq(v, ",")` |

Semantics are identical — each loop body already ignored the index. `SafePath` is invariant
5 (one document, one identity) and `list` feeds `spec.json`, so both are covered by tests
that name the rule; those tests pass unchanged.

Nothing else moved. `intrange`, `usestdlibvars` and `copyloopvar` found nothing new, which
says the tree was already written in idiom ahead of its declared floor — the floor was the
only thing behind.

## Also updated, because a version in two places is one plus a lie

- `.github/workflows/check.yml` and `.github/workflows/pages.yml`: `go-version: "1.26"`.
  **Both** — `pages.yml` was still on 1.22 and had been missed by the earlier lint work.
- `README.md` prerequisites: Go 1.26+, with the apt-vs-tarball trap named there rather
  than only here, because that is the file someone setting up a machine reads.
- `CLAUDE.md` rule 22: "Go 1.22 idiom" → 1.26, naming the `SplitSeq`/`FieldsSeq` iterators
  over their slice-allocating twins, since that is now a lint finding rather than taste.

`internal/server/documents.go` keeps its comment that `{path...}` is "Go 1.22's trailing
wildcard" — that is a statement about which release introduced the feature, and it is still
true.

## Verified

- `go build` and the full test suite (`-count=1`, cache defeated) green on go1.26.5
- `make lint` back to **0 issues** with `modernize` active and no longer muted
- `make check` exit 0 end to end
- the toolchain failure mode reproduced deliberately (above) rather than assumed

Not run: `make check-full`'s browser stages and `make ui`. This change touches no JS and no
markup, and `make ui` would rebuild `web/dist` over unrelated front-end work in progress in
the tree at the time.
